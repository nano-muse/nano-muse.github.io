展示站：七个日常任务案例 ​

nanoMuse 可以读写文件、搜索网页、执行命令、操作浏览器、调用 MCP 服务器和命令行工具，并按技能中的步骤完成任务。在手机上运行时，它还能使用本机日历、剪贴板和闹钟。只有其他方法无法完成任务时，才会操作 App 的屏幕。

工具选择顺序分为四级：先用技能、CLI 或 MCP 服务器，再用带用户登录状态的网页抓取，然后用 App 内浏览器，最后使用手机屏幕。下面七个案例中，只有一个需要操作屏幕。

CLI 指命令行工具；MCP 是让智能体调用外部工具的通用协议；技能是某类任务的操作说明；API 是程序访问服务的接口。操作器则是反复看屏幕、决定动作并执行的组件。其他名词见术语表。

这些案例不会未经确认就消费：发送消息、提交订单或付款前都会暂停等待审批。操作器不填写密码或验证码。各案例使用的服务及测试范围见 services.md。

每个案例的「轨迹」记录已实际执行的过程，可能是 App 保存的聊天时间线，也可能是逐屏展示截图和点击位置的手机记录。「待验证」表示尚未完整跑通，并会注明缺少的条件。四项第一优先级服务的验证需要高德 key、飞书和腾讯会议登录；手机案例需要安装相应 App 的 Android 真机。进度记录在发布清单中。

1. 安排一次出差 ​

明天要去上海开会，下午两点在虹桥附近。帮我看看北京到上海上午出发、下午一点前能到虹桥的高铁，挑一班合适的；查一下从家到北京南站几点得出发；把出发时间写进日历，车次发到飞书的「出差」群。另外记住：我坐高铁只坐二等座、靠窗。

使用的工具执行内容
skills读取 train-tickets 技能。查票使用 12306 服务器，只有用户明确要求时才在手机上订票
remember保存「二等座、靠窗」偏好，供以后处理火车相关任务时使用
12306__get-current-date · get-station-code-of-citys · get-station-code-by-names · get-tickets获取明天日期、北京和上海虹桥的车站代码，查询 13:00 前到达的 G 字头列车、余票和票价。首轮结果无票时再次查询
amap__maps_geo · maps_direction_transit_integrated按已记住的家庭地址规划前往北京南站的路线，计算应在 06:40 前出发
calendar起草出发时间的日历项，包含车次和座位，等待用户确认
shell: lark-cli im +chat-search · im +messages-send --idempotency-key …找到「出差」群并发送消息，先在审批卡片中展示正文

整个过程不操作屏幕。哨兵（Sentinel，检查操作权限的组件）只为群消息请求一次审批，其他步骤均为读取或在用户工作区中操作。

轨迹：车票查询部分已于 2026-09-24 在网页版通过 12306 服务器录制。模型发现 13:00 前到达的二等座已售罄，如实说明并提供最接近的替代车次。高德路线、日历草稿和飞书消息仍待验证，需要测试机上的高德 key 和飞书登录。

2. 生成早间简报 ​

每个工作日早上 7:30 给我一条简报：今天北京的天气、飞书上的日程和没做完的任务、腾讯会议里今天有哪些会，一条通知就好。

使用的工具执行内容
reminders（例程，即定时执行的任务）设置 weekdays 07:30。关闭 App 后仍通过通知送达，手机运行时由闹钟唤醒执行
amap__maps_weather查询北京当天的气温、降雨和空气情况
shell: lark-cli calendar +agenda --as user · task +get-my-tasks --as user获取当天日程和未完成任务，用 --jq 精简返回内容
shell: tmeet meeting list --compact列出当天会议及会议号、链接
通知发送一张通知卡片，点击后在聊天中查看完整简报

轨迹：仍待验证，需要高德 key、飞书和腾讯会议登录。例程和通知机制本身已通过 App 测试及模拟器验证，记录见 archive/android-python-line.md 的持续运行部分。

3. 查询京东订单物流 ​

我上周在京东买的耳机到哪了？

使用的工具执行内容
browser（手机 WebView，即 App 内嵌网页组件）在后台打开京东订单页，不占用前台画面
用户登录遇到登录页时暂停。点击「接管」后，真实网页会在底部面板中打开；用户登录后点「完成」，再交回智能体。登录状态保存在 App 自己的浏览器配置中
browser extract提取订单、运单号和快递公司
kuaidi100__query_trace（已配置时）查询包裹物流；未配置时读取订单页中的物流列表
回复告知包裹当前位置和预计送达时间

这里优先使用第二级方式，即读取带用户登录状态的页面。京东没有个人 API，但网页版可以独立使用，无须先操作手机 App。配置快递100后，物流查询可直接通过工具完成。

轨迹：仍待验证，需要在安装本地版本的手机上登录京东。浏览器后端、接管面板和登录状态保存已在模拟器验证，见 browser.md。

4. 制作成都旅行住宿预算 ​

国庆去成都三晚，住春熙路附近。帮我在去哪儿网上看看每晚 400 元左右、评分 4.5 以上的酒店，挑三家做成预算表存到 trips/chengdu-2026-10/budget.md，只看不订。

使用的工具执行内容
browser（电脑使用 Playwright 自动化浏览器，手机使用 WebView）在去哪儿按日期和区域搜索、筛选酒店，并读取三家酒店的信息
files将酒店名称、位置、每晚价格、三晚合计及评分写入 trips/chengdu-2026-10/budget.md
资源库在 App 内打开并查看预算表

这里使用第三级方式，在后台浏览不需要登录的公开网站，用户可继续做其他事。智能体只查询，不下单；browser 的哨兵规则也会检查下单和付款按钮。

轨迹：仍待验证。2026-09-24 的电脑测试中，去哪儿检测到无头 Chromium（不显示窗口、由程序控制的浏览器），将请求重定向至首页，只显示页脚。执行 21 次工具调用后停止。下一步需要改用手机 WebView，进度见发布清单。

5. 创建会议并通知群成员 ​

下周三下午三点跟设计组开半小时的评审会，用腾讯会议，把会议号发到飞书「设计评审」群。

使用的工具执行内容
calendar检查该时段是否空闲
shell: tmeet meeting create --subject 设计评审 --start 2026-09-30T15:00+08:00 --end 2026-09-30T15:30+08:00在审批卡片中展示完整命令。执行后取得 meeting_code 和 join_url
shell: lark-cli im +messages-send --chat-id oc_… --text "…"在第二张审批卡片中展示包含会议号和链接的群消息
reminders设置提前十分钟提醒

两个命令行工具分别完成创建会议和发送消息，需要两次审批，无须打开 App。轨迹仍待验证，需要在测试机通过 tmeet auth login 和 lark-cli auth login 登录。

6. 把剪贴板中的安排加入日历并设闹钟 ​

（复制了一条消息：「周五上午 10 点，海淀区中关村大街 1 号 3 层会议室，带上合同」）把剪贴板里的这个安排加到日历，提前一小时给我设个闹钟。

使用的工具执行内容
device__clipboard_read读取复制的文字。Android 仅允许 App 在前台读取剪贴板，不满足条件时工具会说明
device__calendar_create创建周五 10:00 的日程，将地址填入地点，将「带上合同」填入备注。首次使用时请求 Android 日历权限
device__alarm_set通过时钟 App 设置周五 09:00 的闹钟
amap__maps_geo（可选）核对地址，并把路程所需时间加到备注中

这些手机本机能力通过 MCP 工具提供，见 device.md。除可选的地理编码请求（将地址转换为地图坐标）外，数据均在本机处理。轨迹仍待验证，需要 Android 手机本地版本，因为设备服务器只在该环境中运行。

7. 在美团选餐，付款前停止 ​

用美团给我点一份公司附近的麦当劳板烧鸡腿堡套餐，送到公司，到付款前停下来。

使用的工具执行内容
在美团里的 phone_task搜索餐厅、选择套餐和地址，胶囊浮层始终显示当前步骤和「停止」按钮
哨兵「提交订单」命中 sensitive_words，属于 SENSITIVE（敏感）操作。Android 真机和托管演示均可在胶囊上选择「允许一次」或「拒绝」，聊天中显示同一个审批请求
停止操作操作器到达付款页后停止并说明情况，由用户在 App 内处理付款

这是七个案例中唯一必须操作屏幕的任务，因为美团没有个人 API，网页版又依赖 App 登录。轨迹会记录操作器看到和执行的内容，并在截图上标出每次点击。

聊天模型负责计划和汇报，由展示站 .env 的 MAIN_MODEL 指定，留空时使用 deepseek-v4.1-flash；屏幕操作模型负责读取截图和选择点击位置，由 GUI_MODEL 指定，使用 qwen3.8-27b。访客使用自有 OpenRouter key 时，屏幕模型为 qwen/qwen3.8-27b。

轨迹：仍待验证，需要安装美团的 Android 真机，x86 模拟器无法运行它。执行器、胶囊和停止机制本身已在模拟器验证，见 gui.md。

已记录但未展示的案例 ​

train-tickets 和 phone-messages 技能还记录了四个屏幕操作案例，都在最终确认前停止，由用户决定是否继续：

  • 交管12123：查询罚单，在付款前停止。
  • 滴滴：填好目的地，在「呼叫」前停止。
  • 12306 App：完成订票准备，在「提交订单」前停止。单纯查票已不需要屏幕操作。
  • 京东 App：整理购物车，在「结算」前停止。

不用于公开演示的内容 ​

用户可以要求智能体读取手机上的微信聊天，但真实微信不会出现在展示站、网站或影片中。托管演示中的微信和铁路12306 都是带预置数据的模拟应用。支付宝账单、医保和个税同样不用于公开演示：这些服务可能禁止自动化，或者数据本身不适合公开展示。

查看执行记录 ​

每个动作都在聊天中显示，例如 12306__get-tickets(…)、shell: lark-cli calendar +agenda --as user 和 phone_act: tap "提交订单" at (318,742) in 美团。审批卡片说明准备执行的动作，以及需要确认的原因。

点击形象后，「活动」（Activity）中保存工具调用和权限判定的审计记录，并注明使用的通道。「权限」（Permissions）显示已有授权，这些案例中的手机步骤授权均仅适用一次。在自己的服务器上，可用 nanomuse phone traces 列出手机任务，用 nanomuse phone trace <id> -o trace.html 导出单个任务，逐屏查看截图和点击位置，见 gui.md → 轨迹。docs/traces/ 中的 Markdown 记录以便于阅读的形式保存同类时间线。

相关技能共有十一个：feishu、tencent-meeting、amap、kuaidi100、train-tickets 对应上述服务，phone-messages 说明屏幕操作，trip-plan、meeting-prep、inbox-triage、compare-options 和 weekly-review 提供任务方法。App 的「技能」（Skills）页列出这些技能。把同名文件夹放入自定义技能目录，即可覆盖相应内置技能。

其他智能体使用的 Agent Skills 格式技能，也可以原样放入 <data_dir>/skills 使用，包括 Larksuite 提供的 lark-* 技能。
